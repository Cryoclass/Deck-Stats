# server — spécifique (complète ../AGENTS.md)

- ESM NodeNext : imports internes avec extension `.js` même vers des sources `.ts` ; `rootDir: "."` → l'entrée compilée est `dist/src/index.js`, les scripts `dist/scripts/*.js`.
- Importe `./env.js` avant tout (index, db, scripts) : le `.env` racine est chargé par chemin explicite ; en conteneur tout vient de l'environnement.
- `src/domain/` = contrat pur partagé avec le web (`deckConfiguration.ts`, `deckArchive.ts`, `deckSummary.ts`, `cardDefaults.ts` — détection des annotations par défaut depuis le texte des cartes, aucune liste de cartes, fenêtres de limite plutôt que phrases) : aucun import Fastify/pg/node. Toute entrée passe par `parseConfiguration`/`parseArchive`/`parseSummary` avant persistance ; `ConfigurationError` → 400.
- `decks.summary` (étape 9A) : cache d'affichage calculé par le client, jamais lu par le serveur ; `PUT /decks/:id` l'accepte en champ de premier niveau (`summary`, hors `configuration`) et l'écrit après `writeConfiguration` dans la même transaction ; `PUT /decks/:id/summary` l'écrit seul pour la révision courante (409 sinon) sans toucher `revision` ni `updated_at` ; les deux refusent un `mainSize` différent du main enregistré (400). `GET /decks` le renvoie tel quel, `GET /decks/:id` renvoie `null`. La version du moteur est une chaîne opaque ici : seul le client (`usableSummary`) la compare.
- `deckRepository.ts` : l'appelant ouvre la transaction (`tx()` de `db.ts`) et verrouille la ligne deck ; lecture et écriture sont complètes (delete + insert), sauf `deck_combo_pairs`, `deck_matchups` et `deck_side_plans` dont les lignes restent stables (upsert) — pour les plans de side, c'est ce qui permet au cache `deck_side_plans.summary` de survivre à un enregistrement qui ne les concerne pas. Jamais d'écriture partielle.
- Routes : auth (`req.user` posé par la garde globale `preHandler`), transaction, `expectedRevision` (409), anciens endpoints partiels → 410. Toute requête bornée à `owner_id` ; ressource d'autrui → 404, jamais 403 ; références croisées validées en SQL, pas en JS.
- Garde (`auth/guard.ts`, audit 04 O1) : décidée sur la route résolue (`req.routeOptions.config`), jamais sur `req.url` (`/%61pi/…` la contournait). Privée par défaut : une route est publique si et seulement si elle porte `config: { public: true }` — aujourd'hui `/api/health`, `register` / `login` / `providers` / `logout`, `discord/start` et `discord/callback` ; `/me` et la déliaison Discord passent par la garde. Le front statique (`WEB_DIST`) est marqué public dans un plugin encapsulé (`markRoutesPublic`), avec son gestionnaire 404 (repli SPA) ; le gestionnaire 404 n'a pas de route résolue et traverse la garde. Toute route ajoutée sans marque est fermée (garde d'`auth.integration.ts`). `requireUser` dans chaque gestionnaire, catalogue compris. Rate-limit opt-in par route.
- `app.ts` = fabrique `buildApp()` (rien n'écoute ; `index.ts` appelle `listen`) ; `setErrorHandler` (audit 04 O10) : une erreur à `statusCode` 4xx garde son message (`ConfigurationError`, `error(404, …)`, 413 / 429 / JSON invalide), tout le reste répond 500 « erreur interne » (détail dans le journal seulement) — jamais un code ni une contrainte SQL au client. `POST /library/categories` et `/groups` ignorent tout `id` client (clé globale, audit 04 O5) ; `DELETE /decks/:id` répond 404 si rien n'est supprimé ; `limit` de la recherche = entier 1..100 ; email d'inscription borné à 254 caractères AVANT la regex (audit 05 C1, gel de la boucle d'événements).
- `card_id` = passcode bigint parsé en Number (`db.ts`) ; aucune FK vers `cards`.
- `db/schema.sql` est idempotent (`if not exists`, blocs `do $$`) et rejoué à chaque déploiement ; les évolutions vont dans `db/migrations/NNN-nom.sql` : `begin` … `commit`, `pg_advisory_xact_lock`, journal `app_migrations`. 001 et 002 sont additives ; 003 (étape 8) est la seule à supprimer : elle purge le modèle historique (`combo_pairs`, `deck_pair_exclusions`, `deck_start_requirements`, `deck_requirements`, `nonengine_categories.relevance`, `card_flags.dead_*`). Le bloc « Modèle historique » de schema.sql ne recrée ces objets que tant que 003 n'est pas journalisée (001 en a besoin sur une base neuve) ; 003 refuse à chaque rejeu tout objet historique réapparu.
- `003-purge-legacy.sql` : aucun psql-isme (exécutable par psql et par le pilote pg des tests) ; modes par GUC de session posée avant le fichier : `testhand.purge_mode = 'simulate'` = exécution réelle dans une sous-transaction annulée volontairement, fin normale (code 0) sur la ligne « SIMULATION TERMINÉE » ; `testhand.purge_accept = '<empreinte>'` exigée pour appliquer dès qu'une ligne est purgée (empreinte md5 des lignes P1–P6 du rapport, recalculée à l'application). Refus nominatifs (001/002 non journalisées, prérequis historique absent de deck_requirements, prérequis v2 sans condition, horizon dans params). Rapport par `select` (stdout) et `raise notice` (même table temporaire).
- Une nouvelle migration se monte dans `docker-compose.yml` et `deploy/docker-compose.prod.yml`, et se rejoue par stdin dans la séquence de `deploy/lib.sh` (`run_migration_sequence`, partagée par `deploy.sh` et `rehearsal.sh`). 001 et 002 ne se rejouent plus une fois 003 journalisée : 001 recréerait `deck_requirements`, que 003 refuse à chaque rejeu. Les additives postérieures se rejouent dans les DEUX branches et AVANT 003 (004 depuis l'étape 10, 005 depuis le back-office, 006 depuis les annotations par défaut) : placées après, leurs tables seraient vues « absentes avant » par le contrôle « 003 n'a touché que ses propres objets ».
- `005-backoffice.sql` (back-office, docs/backoffice.md) : `users.role` (`user` | `admin`, défaut `user`, contrainte `users_role_check`), tables `backoffice_totp` / `backoffice_sessions` / `backoffice_audit` (ajout seul par déclencheur), rôle PostgreSQL `testhand_backoffice` (NOLOGIN, privilèges par colonne, révoqués puis réaccordés à chaque rejeu). Depuis 006, le serveur Node LIT `users.role` (`auth/role.ts` : `/api/auth/me` et la garde `requireReferent`, relu en base à chaque requête, jamais en session) mais aucune route ne l'écrit ; le rôle s'attribue par `deploy/backoffice-role.sh` seulement (`--role referent|admin`, `deploy/backoffice-role.sql`, GUC `testhand.role_*`, simulation par sous-transaction annulée comme 003). Les suites d'intégration Node appliquent 005 (006 l'exige).
- `006-annotation-defaults.sql` (annotations par défaut, docs/annotations-par-defaut.md §13 et compte rendu C) : exige 002 et 005 (refus nominatifs). DDL idempotent HORS journal (le fichier a été étendu après avoir été journalisé en partie B) : CHECK `reactive`, `users_role_check` à trois valeurs, `card_flags.is_hopt` nullable (NULL = hérite ; `default false` conservé, donc toute insertion écrit `is_hopt` explicitement), `card_flags.nonengine_choice`, `nonengine_groups.is_builtin`, `card_references` (référence commune, `updated_by` avec FK), `card_reference_log` (ajout seul par déclencheur `enable always`, `actor` SANS FK : une action `on delete set null` émettrait un UPDATE refusé et bloquerait toute suppression de compte), `grant select` des deux tables à `testhand_backoffice` (005 rejouée APRÈS 006 les retirerait). DONNÉES une seule fois sous le second marqueur `006-annotation-defaults/c` : `is_hopt = false` → NULL (Q2), profil posé → `nonengine_choice`, groupe « Mulcharmy » (2, fourni de base) rétro-créé, `decks.summary` à NULL ; un `update` idempotent serait faux (après C, `false` est un choix). Routes : `GET /library` (+ `choices`, `references`, `referencesVersion` = dernier id du journal, `groups[].is_builtin`), `PUT /library/flags/:id` (copie sur écriture : `inherited` envoyé par le client matérialise l'aspect non-engine hérité ; le serveur ne calcule jamais la détection), `DELETE /library/flags/:id?aspect=hopt|nonengine` (retour au défaut ; les étiquettes restent), `GET /references` (tout compte, + 50 dernières lignes du journal), `PUT` / `DELETE /references/:id` (référent ou admin, sinon 404 ; journal ; aperçus à NULL de TOUS les comptes qui ont la carte). Plafond fourni de base : non supprimable (400), limite modifiable, nom ignoré au PATCH. `account.ts` (`insertAccount`, tous les chemins d'inscription) crée le groupe ; `check-migration.sql` met un KO sur tout compte qui en manque (garde : `auth.integration.ts`).
- Plans de side (étape 10) : `parseConfiguration` valide la STRUCTURE des `matchups` et jamais la cohérence avec les zones ni l'équilibre des listes — un plan devenu incohérent doit rester enregistrable (états « à revoir » et « incomplet » tenus par l'éditeur). Un plan a pour clé naturelle (deck, adversaire, position) ; `deck_side_plans.summary` est un cache d'affichage jamais lu par le serveur, comme `decks.summary`. Étape 10B : `PUT /decks/:id/matchups/:matchupId/plans/:position/summary` l'écrit pour la révision courante (409 sinon) et la taille du main APRÈS échange recalculée depuis le plan enregistré (400 sinon), plan inconnu 404, sans toucher `revision` ni `updated_at` ; `GET /decks/:id` le renvoie dans `plan_summaries`, hors configuration ; aucun enregistrement ne l'efface (l'empreinte, calculée et comparée par le client, en juge).
- Tests node:test via tsx : `tests/*.test.ts` unitaires (`npm test`) ; `npm run test:integration` enchaîne `tests/auth.integration.ts` (audit, lot 1 : app RÉELLE par `buildApp`, garde / chemin encodé / front statique / inscription hostile / erreurs / identifiants serveur ; base vide exigée, réinitialisée à la fin si elle porte ses fixtures ; budgets de débit par IP : 5 inscriptions et 10 connexions par fenêtre, à respecter en ajoutant un test), puis `tests/persistence.integration.ts` (base vide exigée) puis `tests/purge.integration.ts` (étape 8 : réinitialise le schéma public de la base jetable seulement si elle est vide ou porte les fixtures des suites ; fixture `tests/fixtures/legacy-representative.sql` = base de production pré-001 ; faux Supabase HTTP local pour prune-stale-cards). Les trois exigent `TEST_DATABASE_URL=postgres://step23:step23-disposable@127.0.0.1:55433/step23`, conteneur jetable (deploy/configuration-v2.md). Ne pointe jamais un test vers la base de dev.
- Scripts `scripts/*.ts` : simulation par défaut, `--apply` écrit ; garde-fou < 10 000 ids source = abandon ; une carte référencée sans cible sûre est conservée, jamais supprimée. `prune-stale-cards` refuse avant 003, reporte les emplacements v2 (paires par deck avec survivante non concernée, source et feuilles JSON des conditions en jsonpath `strict`, deck_flags, card_flags avec profil et plafond, HOPT tri-état fusionné true > false > null et `nonengine_choice` par OU, `card_references` — deux références = refus ; `card_reference_log` n'est ni compté ni reporté, historique en ajout seul) et annule tout sur conflit non résoluble (deux conditions à fusionner, profils ou plafonds contradictoires). `adopt-legacy` s'exécute avant 001 seulement (base pré-comptes = base pré-001).
- `nonengine_categories.relevance` n'est plus écrite (étiquette pure) : `account.ts`, `decks.ts` (import) et `library.ts` insèrent sans elle ; défaut `'both'` dans schema.sql pour les bases antérieures à 003.
